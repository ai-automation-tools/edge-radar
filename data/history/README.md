# Edge-Radar Trade History

Two log files maintained by the executor and settler. Both are gitignored.

| File | Writer | Purpose |
|------|--------|---------|
| `kalshi_trades.json` | `scripts/kalshi/kalshi_executor.py` | Pre-execution context: composite score, risk approval, edge source, bankroll %, fill status. One record per order placement. |
| `kalshi_settlements.json` | `scripts/kalshi/kalshi_settler.py` | Settled-trade ledger with realized P&L, revenue, fees, ROI. One record per settled trade. Carries the full trade-side context as of R5 (2026-04-27). |

The two files join on `trade_id` (UUID generated by the executor at order time and copied through to the settlement record).

`pending_orders/<client_order_id>.json` holds an order's row from just before its POST until the executor
records the outcome, so it is normally empty. A file that outlives its run means the run died mid-request
or the venue took an order nothing booked; the next `kalshi_settler.py settle` books it if the venue has it
and drops it if not (files under 15 minutes old are left alone, ER-13).

## Backups and restore

None of these files are in git, and the trade-side context (edge, fair value, score, sizing) can't be rebuilt
from Kalshi. The `Reconcile` task's second action runs
`scripts/shared/backup_ledger.py --dest <folder>` nightly: one `edge-radar-ledger_<UTC stamp>.zip` per night,
30 days kept, holding `kalshi_trades.json`, `kalshi_settlements.json`, `trade_journal.jsonl` (if any) and
`shadow_book.json`. The trade and settlement logs are copied under the trade-log lock.

**Restore** (stop the scheduled tasks first, so nothing writes mid-restore):

```powershell
$zip = Get-ChildItem <backup folder> -Filter 'edge-radar-ledger_*.zip' | Sort-Object LastWriteTime | Select-Object -Last 1
$tmp = Join-Path $env:TEMP 'er-restore'
Expand-Archive $zip.FullName $tmp -Force
Get-ChildItem $tmp                                    # check the files and sizes
Copy-Item data\history\kalshi_trades.json data\history\kalshi_trades.pre-restore.json
Copy-Item "$tmp\*" data\history\ -Force
.venv\Scripts\python.exe scripts\kalshi\kalshi_settler.py reconcile   # local log vs Kalshi
```

**Restore drill, quarterly:** expand the newest zip into a temp folder (first three lines above) and check the
JSON files parse and the trade count is close to today's. Don't copy anything into `data\history\`.

## Reconciliation health

Run `python scripts/kalshi/risk_check.py --report reconciliation` to see:

- Trade-log / settlement counts and `trade_id` overlap
- Orphaned-settlement window
- R5-added field coverage (per field, % of settlements where it's populated)

## Pre-R5 historical cohort

Settlements written before 2026-04-27 carry only the legacy schema:

```
trade_id, ticker, side, result, won, contracts, cost, revenue, fees,
net_pnl, roi, edge_estimated, fair_value, market_price_at_entry,
confidence, settled_at
```

R5 (2026-04-27) extended the schema to also carry `order_id`, `title`, `category`, `edge_source`, `closing_price`, `clv`, `composite_score`, `risk_approval`, `bankroll_pct`, `unit_size`, and `fill_status`.

R11 (2026-05-13) added `fair_value_yes` (always YES-perspective probability) and `fair_value_side` (the perspective tag for the legacy `fair_value` field). The legacy `fair_value` field is bet-side perspective in post-R5 records, but pre-R5 entries written before the convention was tightened mixed YES- and NO-perspective values without a tag — making post-hoc NO-side analysis ambiguous. Use `fair_value_yes` for any cross-record probability work; use `fair_value` (still present) for calibration loaders that already assume bet-side.

These pre-R5 records will show as `null` for the R5- and R11-added fields in the reconciliation report. **No backfill is planned** — the missing fields don't exist anywhere on disk and synthesizing them would be fabricating data. Calibration analytics (`scripts/kalshi/model_calibration.py`) read settlement-side fields and degrade gracefully on absent ones; what's lost on this cohort is the ability to slice by composite-score bucket, risk-approval flag, or bankroll allocation.

The trade log itself was reset at some point before 2026-04-27, so 100% of pre-R5 settlements are also orphans (no matching `kalshi_trades.json` entry to join). This is expected and is what motivated R5 in the first place.
